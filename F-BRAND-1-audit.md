## 3. Can outgoing emails show a logo today?

**No — there is currently no logo in any transactional email, and the current
architecture has no image of any kind.** `email_templates.py`'s `_base()`
header (lines 39–46) renders a plain colored `<td>` bar with a `<p>` text
wordmark; there is no `<img>` tag anywhere in the file (confirmed by reading
the full 465-line file).

What would actually be needed to add one, given real email clients can't
resolve local filesystem paths or relative repo paths:

- **Option A — inline base64 embed.** Encode the logo as a data URI and embed
  it directly: `<img src="data:image/png;base64,...">`. Pro: no external
  dependency, works even if images are blocked (though most clients still
  block/warn on `data:` images same as remote ones — Outlook desktop in
  particular has spotty `data:` URI support in HTML email). Con: bloats every
  email's HTML payload; `email_service.py` sends raw `smtplib` MIME messages
  today, so this only needs the string built once as a constant, no new
  attachment/multipart plumbing.
- **Option B — real publicly-hosted image URL.** Host the logo somewhere with
  a stable public HTTPS URL (the MinIO/S3 bucket already used by
  `upload_service.py` is the natural candidate, or a static asset served by
  the frontend/nginx) and reference it as `<img src="https://.../logo.png">`.
  Pro: standard, well-supported pattern, keeps emails small, works reliably
  across Gmail/Outlook/Apple Mail. Con: requires the bucket/URL to be public
  (or the frontend to serve the asset publicly, which it already does for
  `tab-logo.png` today under `/assets/site-logos/`) and reachable from the
  public internet — MinIO's presigned-URL flow used elsewhere in the app is
  for *private* uploads and isn't the right mechanism here; a plain public
  static URL is what's needed.
- **Recommendation for later build work**: Option B, pointing at the same
  publicly-served frontend asset path already used for the favicon, is the
  lower-maintenance choice — no base64 regeneration if the logo changes, no
  payload bloat, and the asset is already served at a stable public URL by
  the existing nginx/frontend setup.

## 4. Color scheme consistency

Both apps define a real token system, and it's the *same* one, defined
independently in each app's `index.css` (Tailwind v4 `@theme` block in
frontend, plain CSS custom properties in kiosk):

| Token | Value | Frontend (`index.css`) | Kiosk (`index.css`) |
|---|---|---|---|
| `--color-primary` | `#1D409C` | ✓ | ✓ |
| `--color-primary-light` | `#8EA0CE` | ✓ | — (not defined in kiosk) |
| `--color-accent` | `#CE1117` | ✓ | ✓ |
| `--color-bg` | `#F8F7FF` | ✓ | ✓ |
| `--color-text` / `--color-dark` | `#1E1B4B` | both names, same value | `--color-text` only |
| `--color-border` | `#E2E0F0` | ✓ | ✓ |
| `--color-muted` | `#6B7280` | ✓ | ✓ |

**These tokens are not consistently applied — there is a lot of hardcoded
duplication that would silently keep the old blue/red palette after a token
swap:**

- `a-mmc_frontend/src/index.css:62` — `.navbar-gradient` (the exact gradient
  behind every "Unicorn" wordmark in Navbar/AdminLayout/StaffLayout) is
  hardcoded to `linear-gradient(135deg, #1D409C 0%, #162f75 100%)` instead of
  `var(--color-primary)` — **defined nine lines below the token itself**, in
  the same file. Changing `--color-primary` in the `@theme` block would not
  change this gradient at all.
- `a-mmc_frontend/src/services/pdfService.js:21-24` —
  hardcodes its own `PRIMARY = [29, 64, 156]` / `DARK = [48, 48, 48]` /
  `MUTED = [102, 102, 102]` RGB arrays. Unavoidable to some extent (jsPDF can't
  read CSS variables from a non-DOM context), but it means a color change
  requires remembering to also edit this file by hand — nothing enforces sync.
- `a-mmc_backend/app/services/email_templates.py` — same issue, worse: colors
  are inlined as literal hex strings directly in the HTML string templates
  (`#1D409C` appears at lines 10, 41, 100, 132; `#CE1117` at lines 11, 377,
  410; `#8EA0CE` at line 115) with no shared constant at all, let alone a
  design-token reference. Twelve separate hardcoded spots to hand-edit.
- `a-mmc_kiosk/src/pages/HomeScreen.jsx:4-5` — re-declares
  `const PRIMARY = '#1D409C'` / `const ACCENT = '#CE1117'` as local JS
  constants instead of importing the CSS vars, then uses them in inline
  `style={}` props (React inline styles can't reference CSS custom properties
  as bare values the way Tailwind arbitrary-value classes can).
- Same re-declaration pattern repeats in `a-mmc_kiosk/src/pages/DirectoryScreen.jsx:5-6`,
  `a-mmc_kiosk/src/pages/KioskTriageScreen.jsx:4-5`,
  `a-mmc_kiosk/src/pages/ClinicianDetailScreen.jsx:9-10`,
  and `a-mmc_frontend/src/pages/admin/AdminAnalytics.jsx:20-21`.
- `a-mmc_frontend/src/components/BodyDiagram.jsx:151-152` and
  `a-mmc_kiosk/src/components/KioskBodyDiagram.jsx:130` hardcode
  `bodyColor="#E2E0F0"` and `highlightedColors={['#8EA0CE', '#1D409C']}`
  as literal props to the third-party `react-body-highlighter` component.

**Lower-priority, not brand-colored**: a long tail of hardcoded grays/status
colors (`#6B7280`, `#9CA3AF`, `#e5e7eb`, `#1e293b`, `#374151`, `#f9fafb`) and
semantic status colors in `AdminAnalytics.jsx:24-29` (`pending` amber
`#F59E0B`, `accepted` green `#22C55E`, `cancelled` red `#EF4444`, `completed`
blue `#3B82F6`, etc.) and one green `#16a34a` in `ClinicianTodayView.jsx:286`.
These aren't MMC-brand-colored and don't need to change for a rebrand, but
they're further evidence the app never centralized color into the token file
consistently — worth a mention, not a blocker.

**Net assessment**: the *primary/accent* brand colors are consistent in value
everywhere (no file uses a different blue or red), so there's no visual
inconsistency today — but a large fraction of that consistency is achieved by
copy-pasting the literal hex values rather than referencing the two CSS
tokens. If MMC's real colors differ from `#1D409C`/`#CE1117`, updating just
`index.css` in each app will miss the `.navbar-gradient` rule, both PDF
generators, all 8 email templates, and five kiosk/frontend page files listed
above — every one of those needs a manual hex-string edit to match.
